03 / Testing and security

What I check before something goes live

I treat launch as incomplete until I have tried to abuse the product the way a stranger would. I only do this on systems I own or have written permission to test. I do not sell “hacking.” I find holes, I patch them, I re-test, I write down what closed.

The pass follows a fixed order: map the real surface, rank the risks, review the code, validate on a staging or local build, fix, then confirm the fix.

  • Threat model What is actually exposed — auth, admin, uploads, webhooks, public APIs — and what would hurt the business first.
  • Authentication Login, sessions, OAuth, JWT, password reset, MFA. Session isolation between roles. Account-takeover paths.
  • Access control IDOR / BOLA, privilege escalation, multi-tenant leaks. Supabase RLS on every table that holds someone else’s data.
  • API authorization REST, GraphQL, gRPC, WebSockets: every endpoint checked for missing authz, not just a login wall on the UI.
  • Injection SQL / NoSQL, command, SSTI, XXE, LDAP/XPath, CRLF. Parameterized queries. No raw user strings in interpreters.
  • Client-side DOM XSS, CSP, CORS, prototype pollution, cache poisoning, clickjacking headers. Output encoding, not hope.
  • Uploads and SSRF File type and size, stored malware paths, URL-fetch features that can hit internal hosts, unsafe deserialization.
  • Secrets Keys and tokens in source, git history, logs, client bundles, and CI. Rotate anything that leaked. Env-only in production.
  • Business logic Pricing, quotas, booking slots, race conditions, workflow skips. The bugs users find when they are greedy, not clever.
  • Chaining and re-test Combine two medium issues into one real path. Patch. Hit the same path again. Score and close the finding.

On the infrastructure side I also set HTTPS, security headers, tight CORS, WAF/bot rules on Cloudflare when the domain is there, and I keep admin routes off the public happy path. Staging first. No destructive tests on production.
